5  Adding a new model

If you have read Section 3 and Section 4, you should have a pretty good idea of how the bmm package functions. Now it’s time to add your new model.

You don’t have to create the files by hand. use_model_template() generates the model file with stubs for every method a model needs, so you can focus on filling them in. The chapter ends with a checklist of everything a new model has to touch outside its own file, because the test suite fails on some of those and review catches the rest.

What use_model_template() does

Run it from the root of the package. It writes R/model_<model_name>.R containing the parameter specification, the model constructor, the user-facing alias, and stub methods for check_data, bmf2bf, configure_model and postprocess_brm. With custom_family = TRUE it also creates one empty inst/stan_chunks/<model_name>_<block>.stan file per entry in stanvar_blocks, wires the code that reads them into configure_model, and adds empty log_lik, posterior_predict and posterior_epred functions that the family already points to.

The full argument list is on the reference page for use_model_template(). Three things about the call are worth knowing:

  • versions is the second positional argument. use_model_template("gcm", TRUE) means versions = TRUE, not custom_family = TRUE. Name the arguments.
  • The stan files are created before the R file is written. If the call fails partway through, empty .stan files are already on disk and you have to remove them by hand before you can call the function again.
  • An unversioned model gets version = "NA" — the literal string, not NA.

What the template leaves for you

The generated file follows the package’s conventions. Two things in it are placeholders that check() will not flag:

  • The prediction functions are empty. With custom_family = TRUE, the family passes log_lik_<model>(), posterior_predict_<model>() and posterior_epred_<model>() to brms, but their bodies are empty, so loo(), pp_check() and posterior_epred() cannot work on your model until you fill them (step 8 below).
  • The settable_links stub is commented out. Uncomment it, so that its tag line reads #' @exportS3Method, if configure_model() builds links into the family or the formulas; otherwise delete it (step 2 below).

There are no stubs for check_formula(), configure_prior(), create_initfun(), revert_check_data() or the optional post-fit methods; add those only if your model needs them.

5.1 Example

Let’s add a new model called gcm. Assume you have tested the model in Stan and have the Stan code ready. We want a custom family with two Stan blocks, likelihood and functions (see ?brms::stanvar for the blocks).

First set up your system and git environment as described in Section 1. Then load the development version with devtools::load_all() and run, from the root directory of the bmm package:

use_model_template("gcm", custom_family = TRUE, stanvar_blocks = c("likelihood", "functions"))

This creates R/model_gcm.R and the empty files inst/stan_chunks/gcm_likelihood.stan and inst/stan_chunks/gcm_functions.stan, and opens them in your editor. The top of the R file holds the specification and the constructor:

.gcm_defaults <- list(
  parameters = list(
    par1 = "Parameter 1 = description of parameter 1",
    par2 = "Parameter 2 = description of parameter 2"
  ),
  links = list(
    par1 = "identity",
    par2 = "log"
  ),
  fixed_parameters = list(
    mu = 0
  ),
  # the sd rate follows the parameter's meaning: 1 for sensitivity, strength,
  # mixing weights and identity-linked drift; 2 for criteria, thresholds,
  # boundary, ndt, start point and log-linked drift; 4 for circular bias
  priors = list(
    par1 = list(main = "normal(0, 1)", effects = "normal(0, 0.5)", sd = "exponential(1)"),
    par2 = list(main = "normal(0, 0.5)", effects = "normal(0, 0.5)", sd = "exponential(2)")
  ),
  init_ranges = list(
    par1 = c(-1, 1),
    par2 = c(0.5, 1.5)
  )
)


.model_gcm <- function(resp_var1 = NULL, required_arg1 = NULL, required_arg2 = NULL,
                                  links = NULL, call = NULL, ...) {
  out <- structure(
    list(
      resp_vars = nlist(resp_var1),
      other_vars = nlist(required_arg1, required_arg2),
      domain = "",
      task = "",
      name = "",
      citation = character(),
      version = "NA",
      requirements = "",
      parameters = .gcm_defaults[["parameters"]],
      links = .gcm_defaults[["links"]],
      fixed_parameters = .gcm_defaults[["fixed_parameters"]],
      default_priors = .gcm_defaults[["priors"]],
      init_ranges = .gcm_defaults[["init_ranges"]]
    ),
    class = c("bmmodel", "gcm"),
    call = call
  )
  out <- set_links(out, links)
  out
}

# uncomment if configure_model() builds the links into the family or into
# the non-linear formulas rather than reading them from the list above,
# so that a link set by the user is refused instead of silently ignored:
# #' @exportS3Method
# settable_links.gcm <- function(model) character(0)

Above the specification, a header comment lists the registries outside the file that a new model must update (see Before you open the pull request). Below it come the user-facing alias gcm() with its roxygen block, and the stubs check_data.gcm(), bmf2bf.gcm(), configure_model.gcm() (with a custom_family() skeleton and the lines that read your two Stan files), log_lik_gcm(), posterior_predict_gcm(), posterior_epred_gcm() and postprocess_brm.gcm(). The check_data, bmf2bf and postprocess_brm stubs carry a header comment saying when you may delete them.

For a complete model written to the current conventions, read R/model_sdt_yn.R: a custom family on aggregated counts, with its own log_lik, posterior_predict and posterior_epred functions and a settable_links method. Most of its length is documentation.

5.2 Filling in the template

  1. The specification and the constructor. Most of your work is in .gcm_defaults: the parameters (with descriptions), their links, which parameters are fixed and to what value, the default priors, and the initialization ranges. Set default priors (main, effects and sd) for every parameter, informed by knowledge in the field; .ddm_defaults in R/model_ddm.R is a worked example. Give init_ranges only to parameters whose likelihood is undefined in part of their range, such as a non-decision time that must stay below the fastest RT (see Section 3.10). Prefer parameter names of more than one letter that do not match a likely data column (see Failure modes to expect).

    In .model_gcm(), rename the response and required arguments and fill in the metadata (domain, task, name, citation, requirements). Two things about the constructor are checked by tests: it must run with no arguments (the tests call every .model_*() bare, which is why every argument defaults to NULL), and its fields must stay in the order the template emits them. For domain, reuse the string of the models your model sits with, so that supported_models() and the website list it under the right task group: "Visual working memory", "Working Memory (categorical), Categorical Decision Making", "Perception & Recognition Memory" (or "Recognition Memory", which lands in the same group) or "Decision Making / Response times". A new string becomes a group of its own.

    For a model with several versions, generate the scaffold with use_model_template("gcm", versions = c("v1", "v2")). You get a .gcm_version_table with one entry per version, a constructor that reads each field from it and appends paste0("gcm_", version) to the class, and an alias with version = c("v1", "v2") validated by match.arg(). Keep the default as a literal c(...): model_versions() reads it to build the per-version documentation tables.

  2. Links. The constructor passes the user’s links through set_links(), which refuses names that are not parameters, repairs one-letter typos with a warning, and warns when a link widens the parameter’s range (say identity instead of log). By default every link in your links list can be changed by the user. If configure_model() writes a link into the family, the Stan code or the non-linear formulas instead of reading it from the list, a user’s choice would be silently ignored, so declare which links can be set:

    #' @exportS3Method
settable_links.gcm <- function(model) character(0)   # or c("par1")

    Name the method for your model class, not for bmmodel, which comes first in every class vector and would shadow it. A model that substitutes the inverse link into its formulas itself also overrides settable_link_functions(); the multinomial SDT models are the examples.

  3. The user-facing alias. Rename the required arguments and fill in @examples with a full example. Keep the generated @keywords bmmodel: the pkgdown test needs it and is skipped inside check() (see Chapter 6). Title and details are generated from the constructor.

  4. check_data.gcm() checks the data and returns it, ending with NextMethod("check_data"). It may compute transformations or store values as data attributes for configure_model (see Section 3.6). If it adds, renames or packs columns, update() needs to undo that before it can re-run it on a fitted model’s data; see Section 3.7.

  5. bmf2bf.gcm(), if needed. You need a custom method if your model has several response variables (DDM: rt | dec(response) ~ 1), uses aggregate data through vreal(), vint() or trials() (EZDM, sdt_yn), or needs other response wrapping. brms reads this formula as the linear model for the family’s mu. If your model has no natural mu, suppress it: put mu = 0 in fixed_parameters, add a dummy mu (identity link) to the family’s dpars, and write the first formula line yourself (see Section 3.9). Leave the dummy mu out of parameters, so that prior_info() and parameter_info() do not report it.

  6. configure_model.gcm() builds the formula, the family and the stanvars and returns nlist(formula, data, stanvars). It does not return initial values. brms connects the family to your Stan code by name: a custom family "gcm" with dpars = c("mu", "par1", "par2") calls a Stan function gcm_lpdf(y | mu, par1, par2) (gcm_lpmf for an integer response) that you define in gcm_functions.stan. The SDM and DDM methods in Chapter 4 show the whole pattern, and the brms custom families vignette explains it. Add further Stan files to inst/stan_chunks/ and read them here. If your Stan code has to differ when the user asks for within-chain threading, see Section 3.11.

  7. postprocess_brm.gcm() changes the fitted object (renaming parameters and the like). Delete the section if you need none.

  8. log_lik, posterior_predict and posterior_epred, for a custom family. These are plain R functions passed to brms::custom_family(); the template generates them empty and already passes them to the family, and their contracts are in Chapter 6. They power LOO and WAIC, posterior predictive checks, and posterior_epred()/fitted(). Build them on d*() and r*() functions for your model in R/distributions.R, which you write first (see Distribution functions). If the mean of your response is not a useful quantity, pass posterior_epred_undefined("gcm"), as SDM does, so the user gets an error that points to native_parameters(). Models built on a native brms family (brms::mixture(), brms::multinomial()) get all three from brms.

5.3 Before you open the pull request

Everything below lives outside your model file.

The test suite fails without these:

  • An entry in data_column_roles (R/helpers-model.R) labelling each alias argument without a default: what the data column holds, in a few words. Use <model>_<version> keys where versions differ, and NA for an argument that names no column. Copy the entry of a similar model. The Get started article builds its model tables from it.
  • A case in stored_frame_cases() in tests/testthat/test-update.R (a model, a formula and a small dataset, like the cases already there), and a revert_check_data() method if your check_data() changes columns (Section 3.7).
  • Your model working in the loop of "check_data() returns a data.frame()" in tests/testthat/test-helpers-data.R. The loop calls every constructor with a shared set of arguments and a shared data frame; add a branch for your model if those do not fit it, as sdt_ranking and sdt_cdp have, or exclude it with a pointer to its own test, as sdt_rating is.
  • @keywords bmmodel on the alias, and a constructor that runs without arguments and keeps the template’s field order.

Review expects these:

  • A branch in response_annotations() (R/helpers-model.R) giving the coding each response variable needs (“radians in [-pi, pi]”, “seconds”). print() shows it next to each response.
  • A domain that places the model in the right task group (step 1).
  • A test file, a parameter recovery study, an example dataset, an article, and a NEWS.md entry (below and Chapter 6).

Optional extension points. The defaults cover most models; implement one only when its condition applies.

Method Implement when Example
pp_observables(), pp_simulate() the likelihood has more than one observable (RT and choice, counts and means), so pp_check() should check each. Add the model to registered_models in test-pp_observables.R. R/model_ddm.R
native_transform() the map from sampling to native scale is not elementwise links plus at most one softmax group, or depends on the design native_transform.non_targets()
data_check_findings() users commonly make a data mistake that check_data() tolerates; bmm_data_check() reports it data_check_findings.circular()
create_initfun(), configure_prior() init_ranges and default_priors cannot express what the model needs create_initfun.m3()

A model fitted to aggregated counts can also be added to uses_aggregate_data() in R/data_check.R (currently m3 and ezdm), so that bmm_data_check() does not note too few observations per cell.

5.4 Failure modes to expect

configure_prior() errors if fixed_parameters names a parameter the formula never gets. Every name in fixed_parameters has to be wired into the formula by your configure_model(), as either a distributional parameter or a non-linear one. This is the error you get when you add mu = 0 to fixed_parameters but forget the dummy mu in the family’s dpars.

Short parameter names are risky. create_initfun() maps Stan parameter names back to your model parameters with the regex (^|_)param(_|$), taking the longest match. A parameter called s therefore matches b_s_Intercept but not b_sim_Intercept. A name that is a substring of another is safe; a name that appears as a whole underscore-delimited token elsewhere in the Stan parameter names is not.

A predictor that is also a parameter name and also a data column warns. bmm decides whether a formula component is non-linear by whether one of its predictors is also a predicted parameter. When the same name is a data column too, that choice changes the likelihood without the user seeing it, so check_formula() warns. One-letter parameters collide with columns like a condition coded c; another reason to avoid them.

Method signatures follow the generics. bmm() calls create_initfun() with the prior as a fourth argument, so a method written as function(model, data, formula) fails on every fit. configure_prior() methods receive data2, knots or drop_unused_levels through ... when the user passes them, so a method without ... fails only then, which is the case nobody tests. R CMD check flags both. The full table is in Chapter 3.

5.5 Testing

Test your model with testthat; use_test() creates the file. tests/testthat/test-model_ddm.R and test-model_sdt_yn.R show how models are tested. Fitting takes too long for the test suite, so pipeline tests use brms’ mock backend. backend = "mock" is a brms::brm() argument, and mock_fit reaches brms’ mock backend through brm()’s ..., just as both reach brm() through bmm()’s ...: whatever you pass as mock_fit is returned in place of the fitted Stan object. Everything before the fit — data checks, formula translation, family construction, stanvars, priors, initial values — runs for real, which is what you want to test:

test_that("gcm model runs without errors", {
  withr::local_options("bmm.silent" = 2)
  skip_on_cran()

  dat <- data.frame(
    resp = rnorm(10),
    exemplar = rep(c("A", "B"), 5),
    category = rep(c(1, 2), each = 5)
  )

  f <- bmmformula(par1 ~ 1, par2 ~ 1)
  mock_fit <- bmm(
    f, dat,
    gcm(resp_var1 = "resp", required_arg1 = "exemplar", required_arg2 = "category"),
    backend = "mock", mock_fit = 1, rename = FALSE
  )
  expect_equal(mock_fit$fit, 1)
})

Two things about that call are easy to get wrong. The alias calls stop_missing_args(), so every argument without a default has to be supplied. And the argument is mock_fit. Older test files write mock = 1, which works only because R partial-matches it to mock_fit on the way through ....

tests/testthat/helper-epred.R provides epred_vs_predict() and expect_epred_by_cell() for testing a posterior_epred function against the mean of posterior_predict. If your Stan code switches on threading, test the generated code with and without threads, as test-model_sdm-stancode.R does.

The tests run with every check(). Make sure all of them pass before you submit.

5.5.1 Parameter recovery

Also run the model in a separate script on simulated data and check that it recovers the parameters: the hyper-parameters (means and standard deviations) and the subject-level parameters, with enough conditions to tell users how much data they need. Chapter 6 covers what the study has to show, in particular why you must not simulate and fit with the same distribution function, and how to report it.

5.5.2 Distribution functions

A custom family also needs distribution functions in R/distributions.R: d* and r*, optionally p* and q*. They are used to simulate data, inside log_lik, posterior_predict and posterior_epred, and for plotting.

5.6 Post-processing infrastructure

Most of the post-fit tools read the model object and need no code from you:

  • conditional_effects() and the emmeans integration work through the bmmfit class.
  • native_parameters() returns posterior draws of the parameters on their native scale, using your links through the default native_transform() method.
  • parameter_info() and prior_info() read parameters, fixed_parameters, links and the default priors. A parameter in fixed_parameters but not in parameters (a dummy mu) is treated as family machinery and left out of the prior_info() report.
  • posterior_epred() and fitted() call the posterior_epred function of your family. Models with class "circular" refuse them, because the mean of a circular error is not useful.
  • pp_check() checks the brms response by default; pp_observables() extends it to further observables.
  • bmm_data_check() runs your check_data() without compiling and adds anything your data_check_findings() method reports.

5.7 Add an example dataset

Every new model needs an example dataset that users can load and that the examples use. It can be a new dataset added to the package, one already in the package, or one from another package loaded with data(). The mixture2p and mixture3p articles use data('bays2009_full', package='mixtur'); the IMM and the SDT models use datasets shipped with bmm. For how to add one, see R Packages.

5.8 Add an article

Every new model needs an article explaining the model and how to fit it with bmm. Create it with use_article() (see R Packages); the existing ones are in vignettes/articles/, and the published versions are here. The README, the home page and the Get started tables list your model automatically, from its constructor and its data_column_roles entry.

Then submit your pull request.
